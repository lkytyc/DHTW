HCOME Reproduction - Human Participation and Input Specification Handbook
Version: 1.0
Language: English
Last updated: 2026-01-28

=====================================================================
0. Purpose and Scope
=====================================================================
This handbook is for users who want to reproduce or run the four system
levels in this project: Level-0, Level-1, Level-2, and Level-3.

It explains:
1. The human role, interaction pattern, and input/feedback requirements at
   each level.
2. How to fill in `project_input.yaml`, with a reusable template.
3. How to prepare `source_text.txt` as the source material.
4. Typical feedback templates that can be copied directly.
5. Common mistakes and validation checkpoints that help keep outputs stable
   and reproducible.

This handbook covers human-computer interaction and input conventions only.
It does not explain the code structure or the underlying modeling theory.

=====================================================================
1. Shared Assumptions and Directory Conventions
=====================================================================
1.1 Required Input Files

A) `project_input.yaml`
- Describes the project goal, domain information, output settings,
  competency questions, and rules.
- This file is reusable. The same template can be adapted to multiple
  domains such as API, city, language, or others.

B) `source_text.txt`
- Contains the source material, one sentence per line.
- This is the evidence source used to build the ontology/schema.
- Prefer factual statements about concepts, relations, and attributes.
- Avoid long paragraphs or mixed formatting whenever possible.

1.2 Output Directory Convention

Each run produces:
`outputs/<timestamp>_L{level}/batch_{i}/`

Each batch directory contains at least:
- `ontology.ttl` for the final ontology in TTL format
- `schema.json` exported from the TTL
- `conversation.md` containing the interaction and model output for auditing

Intermediate files may also appear, such as:
- `round*_design.md`
- `round*_simulation.md`
- `full_output.md`

1.3 Interaction Convention

Level-0, Level-1, and Level-2 use a stable interaction pattern:
- Multi-line input is allowed.
- End a multi-line input block by typing `END` on a separate line.
- When the system asks whether to continue iteration, you must explicitly
  enter `y` or `n`. Empty input is not accepted.

=====================================================================
2. Overview of the Four Levels
=====================================================================
Level-0: HCOME
- Human involvement: high
- System role: provides a strict and auditable manual input workflow and
  produces minimal TTL plus `schema.json`
- Interaction: multiple rounds; you may add classes, relations, and
  properties in multiple passes
- Suitable when: you want maximum structural control or want to establish a
  gold-standard skeleton first

Level-1: X-HCOME
- Human involvement: medium to high
- System role: the model proposes a candidate design first; the human
  iteratively refines it until a final TTL plus `schema.json` is produced
- Interaction: iterative, until you enter `n` or the run reaches
  `max_rounds`
- Suitable when: you want a high-quality schema quickly and are willing to
  provide several rounds of corrective feedback

Level-2: SimX-HCOME
- Human involvement: medium
- System role: the model simulates a discussion among roles such as
  KE/DE/KW, then the human supervisor intervenes when needed, and the system
  produces the final TTL plus `schema.json`
- Interaction: iterative, until you enter `n` or the run reaches
  `max_rounds`
- Suitable when: you want the model to debate internally first and let the
  human step in only for key corrections

Level-3: Sim-HCOME
- Human involvement: low
- System role: generates TTL plus `schema.json` in a single shot
- Interaction: no in-process interaction; this aligns with the paper's
  "single prompt, no human intervention" setting
- Suitable when: you want batch construction or a fully automated pipeline

=====================================================================
3. Level-0 (HCOME): Human-Driven Specification Workflow
=====================================================================
Goal: manually define Classes, Object Properties, and Data Properties, then
produce usable TTL plus `schema.json`.

3.1 Your Role
- Supervisor / Knowledge Engineer
- One person can play both roles
- You are responsible for naming concepts, relations, and attributes, and
  for keeping the semantics precise and consistent

3.2 Step-by-Step Workflow

Step 0: Prepare `project_input.yaml`
- At minimum, provide `output.namespace_prefix`, `output.base_iri`, and
  `domain.name`

Step 1: Run Level-0
- `python level0_hcome.py`

Step 2: Enter `Classes`
- One class per line
- Optional format:
  `ClassName: definition`
- Finish the block with `END`
- The system then asks:
  `Add more Classes? (y/n)`

Step 3: Enter `Object Properties`
- Recommended format:
  `propertyName | domainClass | rangeClass | definition`
- `domainClass` and `rangeClass` should refer to classes already defined, or
  classes you intend to define consistently
- Finish the block with `END`, then answer `y` or `n`

Step 4: Enter `Data Properties`
- Format:
  `propertyName | domainClass | rangeType | definition`
- Recommended `rangeType` values:
  `string`, `number`, `boolean`, `xsd:string`, `xsd:decimal`,
  `xsd:boolean`
- Finish the block with `END`, then answer `y` or `n`

Step 5: Output
- `batch_1/ontology.ttl`
- `batch_1/schema.json`

3.3 Naming and Modeling Rules
- Classes: use `PascalCase`, for example `City`, `LanguageFamily`
- Object and data properties: use `lowerCamelCase`, for example
  `belongsToClass`, `hasISOCode`
- One property should represent one meaning only
- Avoid vague names such as `uses` when a more precise name is possible, for
  example `usesHTTPMethod`
- Do not model concrete instances as classes unless the source material truly
  requires it

3.4 Recommended Level-0 Draft Template

Classes:
Class
Method
Service
Endpoint
HTTPMethod
City
Country
Language
LanguageFamily
END

Object Properties:
belongsToClass | Method | Class | Method belongs to a Class
belongsToService | Endpoint | Service | Endpoint belongs to a Service
usesHTTPMethod | Endpoint | HTTPMethod | Endpoint uses an HTTP method
locatedIn | City | Country | City is located in a country
belongsToFamily | Language | LanguageFamily | Language belongs to a family
END

Data Properties:
name | Class | string | Human-readable name
name | Method | string | Human-readable name
hasISOCode | Language | string | ISO code
returnType | Method | string | Return type
parameters | Method | string | Parameters represented as a JSON string
END

4. Level-1 (X-HCOME): Human-in-the-Loop Iterative Refinement
=====================================================================
Goal: improve a candidate schema through iterative supervisor feedback, then
produce TTL plus `schema.json`.

4.1 Your Role
- Supervisor

You are responsible for:
- deciding whether the abstraction level is appropriate
- checking whether the classification is clear
- checking whether relation domain/range assignments are correct
- detecting duplicate concepts and requesting merge or rename operations
- limiting scope to avoid hallucination

4.2 Workflow

Step 0: Prepare inputs
- `project_input.yaml`
- `source_text.txt`, one sentence per line

Step 1: Run Level-1
- `python level1_xhcome.py`

Round 1
- The system generates candidate classes, properties, and clarification
  questions
- Output is saved to `batch_i/round1_design.md`

Round k, for k >= 2
Step 2: The system prompts for optional supervisor feedback
- Enter multiple lines
- Finish with `END`

Step 3: The system performs one revision
- Output is saved to `batch_i/round{k}_design.md`

Step 4: The system asks:
- `Continue iteration? (y/n)`
- Enter `y` to keep refining
- Enter `n` to stop and finalize

Final output:
- `ontology.ttl`
- `schema.json`

4.3 How to Write Feedback

Feedback should be actionable and checkable. Recommended action verbs:
- Add
- Remove
- Rename
- Merge
- Split
- Fix domain/range
- Add constraint
- Clarify modeling choice
- Tighten scope

Avoid vague comments such as:
- "make it better"
- "make it more abstract"

Instead, state exactly what should be changed.

4.4 Minimal Feedback Templates

Template A: lightweight correction
Overall direction is acceptable. Please make the following adjustments:
1. Model `hasISOCode` as a data property of `Language` with range `string`,
   instead of turning ISO code into a class.
2. Keep `parameters` and `returnType` as strings for now; `parameters` may
   contain a JSON string.
3. Restrict the domain of `name` to the main classes only.
END

Template B: clarify the abstraction hierarchy
Please make the abstraction clearer:
- Introduce a super-class `APIEntity` that covers `Class`, `Method`,
  `Service`, and `Endpoint`
- For geography, use `Place -> City`, and keep `Country` as an administrative
  unit
- For language, introduce `Dialect` only if the material explicitly supports
  it
- Merge synonyms and standardize names, for example rename `uses` to
  `usesHTTPMethod`
END

4.5 When to Stop Iterating

It is usually safe to stop when most of the following are satisfied:
- competency questions are substantially covered
- naming is consistent and duplicate concepts are gone
- domain/range choices are reasonable
- the TTL can be opened in Protege
- your remaining edits are minor rather than structural

4.6 How Many Rounds Should You Use

The paper emphasizes "iterate until satisfied" rather than a fixed number of
rounds. In practice, `iteration.max_rounds` is used as an upper bound to
prevent infinite loops. Values such as 5 or 8 are often reasonable.

5. Level-2 (SimX-HCOME): Supervisory Intervention over Simulated Discussion
=====================================================================
Goal: let the model simulate a KE/DE/KW discussion first, then intervene as a
supervisor when necessary before producing TTL plus `schema.json`.

5.1 Your Role
- Supervisor

Your job is to:
- correct modeling bias or drift that appears in the simulated discussion
- make decisions on key modeling questions when the draft is ambiguous

5.2 Workflow

Step 0: Prepare `project_input.yaml` and `source_text.txt`
Step 1: Run Level-2
- `python level2_simxhcome.py`

Round 1
- The system simulates the discussion
- Output is saved to `batch_i/round1_simulation.md`

Round k
- You provide supervisor intervention in multiple lines
- End with `END`
- The system produces the next revised simulation result
- The system asks whether to continue with `y` or `n`

Final output:
- `ontology.ttl`
- `schema.json`

5.3 Intervention Style

Compared with Level-1, Level-2 interventions should be slightly more
decision-oriented. Example guidance:
- Prefer reusable abstractions such as `Entity`, `Role`, or `Event` only when
  the source material supports them
- Do not convert concrete method names directly into classes
- If GET or POST appears, treat them as instances or controlled vocabulary
  items under `HTTPMethod`
- If multiple domains appear, favor modularization, for example API, Geo, and
  Language sharing a small core

6. Level-3 (Sim-HCOME): Single-Shot Input Specification
=====================================================================
Goal: produce TTL plus `schema.json` in one shot using only
`project_input.yaml` and `source_text.txt`.

6.1 Your Role
- Data provider and result reviewer

You only need to:
- prepare high-quality source material in `source_text.txt`
- prepare the project goals and output settings in `project_input.yaml`
- review the generated `schema.json` and `ontology.ttl`
- if necessary, fall back to Level-1 or Level-2 for refinement

6.2 Workflow

Step 0: Prepare `project_input.yaml` and `source_text.txt`
Step 1: Run Level-3
- `python level3_simhcome.py`
Step 2: Review
- `batch_i/schema.json`
- `ontology.ttl`

7. `source_text.txt` Input Specification
=====================================================================
Goal: give the model enough evidence to extract concepts and relations
reliably.

7.1 Basic Format
- One sentence per line
- Prefer declarative sentences
- Ideally, each line should contain one fact, relation, or attribute

7.2 Recommended Sentence Patterns

Entity typing:
- `A <Type> is a kind of <SuperType>.`

Attributes:
- `A <Type> has <attribute>.`

Relations:
- `A <TypeA> <relation> a <TypeB>.`

Constraints:
- `Each <Type> must have exactly one <relation>.`

Only write constraints that are genuinely supported by the source material.

7.3 Cross-Domain Examples

API:
- `A Class has a name.`
- `A Method belongsToClass a Class.`
- `An Endpoint belongsToService a Service.`
- `An Endpoint usesHTTPMethod an HTTPMethod.`

Geo:
- `A City is a type of Place.`
- `A City isLocatedIn a Country.`

Language:
- `A Language belongsToFamily a LanguageFamily.`
- `A Language hasISOCode as a string.`

8. `project_input.yaml` Input Specification
=====================================================================
8.1 Recommended Top-Level Fields

domain:
  name:
  aim:
  scope:
  target_users:
  reuse_policy:

requirements:
  must_cover:
  constraints:

competency_questions:
rules_nl:

output:
  format: "ttl"
  namespace_prefix: "ex"
  base_iri: "http://example.org/schema#"
  protege_version_hint: "5.6.3"

iteration:
  max_rounds: 3

prompts:
  language: "English"

8.2 Minimum Required Fields
- `domain.name`
- `domain.aim`
- `requirements.must_cover`
- `requirements.constraints`
- `output.namespace_prefix`
- `output.base_iri`
- `output.format`

8.3 Reusable Template

domain:
  name: "GenericSchema"
  aim: "Build a domain-agnostic schema/ontology from provided text materials."
  scope: "Model only what is supported by the materials; avoid unsupported assumptions."
  target_users:
    - "Analysts"
    - "Engineers"
  reuse_policy: "Reuse common patterns only when present or clearly helpful."

requirements:
  must_cover:
    - "Core entity types"
    - "Relationships"
    - "Attributes"
    - "Constraints if supported by the materials"
    - "Consistent naming and deduplication"
  constraints:
    - "No hallucination: only assert what the materials support"
    - "Classes use PascalCase and properties use lowerCamelCase"
    - "Prefer a small, extensible core"
    - "If multiple domains appear, keep the design modular"

competency_questions:
  - "What are the main entity types mentioned?"
  - "What attributes does each entity type have?"
  - "What relationships exist between entity types?"
  - "What constraints or requirements are implied?"
  - "How do types relate through subclass or part-of relations?"

rules_nl:
  - "If an entity has an identifier, treat it as a key candidate when supported."
  - "If something is part of something else, prefer patterns such as partOf or locatedIn."

output:
  format: "ttl"
  namespace_prefix: "ex"
  base_iri: "http://example.org/schema#"
  protege_version_hint: "5.6.3"

iteration:
  max_rounds: 3

prompts:
  language: "English"

8.4 Common Mistakes
- Writing a literal API key in `api_key_env` instead of an environment
  variable name
- Putting multiple facts on one line in `source_text.txt`
- Asking too many competency questions when the material does not support
  them
- Giving abstract feedback without executable instructions
- Reusing a generic property such as `name` across too many unrelated classes
  without checking TTL compatibility

=====================================================================
9. Research-Style Writing Advice for Feedback and Intervention
=====================================================================
- Use itemized, verifiable language
- State clearly what to add, remove, rename, merge, or constrain
- Specify the intended domain and range when relevant
- If the material does not support a claim, write either:
  `Assumption: ...`
  or
  `Not enough evidence; leave it out.`

10. Quick-Use Checklist
=====================================================================
A) If you want fast fully automated output, use Level-3
1. Write `source_text.txt` with one sentence per line
2. Write `project_input.yaml`
3. Run `python level3_simhcome.py`
4. Review `batch_1/schema.json` and `ontology.ttl`

B) If you want controlled high quality, use Level-1
1. Run `python level1_xhcome.py`
2. Enter feedback in multiple lines, then finish with `END`
3. Answer `Continue iteration? y/n`
4. Stop with `n` when you are satisfied
5. Review `batch_1/schema.json`

C) If you want the model to debate first, use Level-2
1. Run `python level2_simxhcome.py`
2. Enter intervention text, then finish with `END`
3. Control iteration with `y` or `n`

D) If you want a manual gold-standard skeleton, use Level-0
1. Run `python level0_hcome.py`
2. Enter Classes, Object Properties, and Data Properties using `END` and `y/n`
3. Review `schema.json`
